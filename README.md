# 🤖 Policy RAG Assistant

![Python](https://img.shields.io/badge/Python-3.10+-3776AB?style=for-the-badge&logo=python)
![Streamlit](https://img.shields.io/badge/UI-Streamlit-FF4B4B?style=for-the-badge&logo=streamlit)
![Gemini](https://img.shields.io/badge/LLM-Gemini-8E75B2?style=for-the-badge&logo=googlegemini)

ผู้ช่วย AI ที่อ่านนโยบายและระเบียบปฏิบัติทั้งหมดขององค์กรแทนคุณ พิมพ์คำถามเป็นภาษาไทยธรรมดา แล้วได้คำตอบพร้อมอ้างอิงรหัสเอกสารและหัวข้อทันที — ไม่ต้องเปิดไฟล์ทีละฉบับ ไม่ต้อง Ctrl+F หาทีละคำ

ออกแบบมาให้ **ใช้ได้กับองค์กรไหนก็ได้** ไม่ผูกติดกับบริษัทใดบริษัทหนึ่ง แค่ตั้งค่าเอกสารกับชื่อองค์กรผ่านไฟล์ `.env` ก็พร้อมใช้งาน

---

## ✨ ฟีเจอร์เด่น

- **🔍 ค้นหาแบบเข้าใจความหมาย ไม่ใช่แค่ keyword** — ใช้ BGE-M3 (embedding) ร่วมกับ BGE-reranker-v2-m3 (reranker) ถามด้วยคำพูดธรรมดาที่ไม่ตรงกับข้อความในเอกสารเป๊ะๆ ก็ยังหาคำตอบที่ใช่ได้
- **🧠 จำบทสนทนาในเซสชัน** — ถามคำถามต่อเนื่องได้โดยไม่ต้องพิมพ์บริบทซ้ำ ระบบจำสิ่งที่คุยกันไปแล้ว
- **📎 อ้างอิงแหล่งที่มาทุกครั้ง** — ทุกคำตอบแนบรหัสเอกสารและหัวข้อที่ใช้อ้างอิง ตรวจสอบย้อนกลับไปที่ต้นฉบับได้เสมอ ไม่ตอบมั่ว
- **🏢 ปรับแบรนด์ได้โดยไม่ต้องแก้โค้ด** — ตั้งชื่อองค์กรผ่านตัวแปร `COMPANY_NAME` ใน `.env` ไฟล์เดียวกันนี้ deploy ให้กี่บริษัทก็ได้
- **🛡️ ทนทานต่อการใช้งานยาวๆ** — แยกโปรเซสประมวลผล AI ออกจากหน้าเว็บ Streamlit โดยสิ้นเชิง (ดูเหตุผลด้านล่าง) หน้าเว็บไม่ค้าง ไม่ล่มกลางดึก
- **💾 เอกสารไม่ออกจากเครื่อง** — ทุกขั้นตอนรันบนเครื่องของคุณเอง 100% ยกเว้นการเรียก Gemini API เพื่อสรุปคำตอบ
- **📝 ร่างนโยบายใหม่ + ตรวจสอบตัวเองอัตโนมัติ (ทดลอง)** — ไม่ใช่แค่ค้นหาของเดิม แต่งร่างนโยบายใหม่ทั้งฉบับได้ในคลิกเดียว โดยอ้างอิงนโยบายเดิมให้สอดคล้องกัน พร้อมรายงานจุดที่ต้องระวังก่อนนำไปใช้จริงในทันที ดูรายละเอียดด้านล่าง
- **💬 คุยต่อเรื่องร่างในแชทได้ (เฉพาะเซสชันเดียวกัน)** — หลังสร้างร่างเสร็จ กลับไปโหมดถาม-ตอบปกติแล้วถามต่อเกี่ยวกับร่างนั้นได้เลย (เช่น "อธิบายข้อ 3 ในร่างให้หน่อย") ระบบติดป้ายกำกับชัดเจนว่าเป็นเนื้อหา AI สร้างที่ยังไม่อนุมัติ ไม่ปนกับนโยบายจริง
- **📋 ตรวจทานนโยบายเดิมทีละหัวข้อ (ทดลอง)** — นอกจากร่างใหม่ ระบบยังช่วย "รีวิว" เอกสารที่มีอยู่แล้วได้ด้วย วิเคราะห์โครงสร้างหัวข้อของเอกสารเป้าหมายอัตโนมัติ แนะนำเอกสารที่เกี่ยวข้องให้ตรวจร่วมกัน แล้วเดินตรวจทีละหัวข้อพร้อมข้อมูลช่วยกรอกจากเอกสารจริง ดูรายละเอียดด้านล่าง
- **❓ คำถามก่อนร่าง/รีวิวแบบทีละข้อ พร้อมข้อมูลช่วยกรอก** — ทั้งโหมดร่างเอกสารและโหมดรีวิว ถามคำถามทีละข้อ (ไม่ใช่ฟอร์มเดียวรวด) แบ่งหมวดหมู่ชัดเจนและละเอียดขึ้น ย้อนกลับไปแก้คำตอบก่อนหน้าได้ และก่อนแต่ละคำถามระบบจะเสนอคำตอบที่น่าจะเป็นจากเอกสารจริงมาให้ยืนยัน/แก้ก่อนเสมอ (Prefill)
- **🔁 สลับโมเดลสำรองอัตโนมัติเมื่อชนโควตาหรือค้างนานเกินไป (ไม่บังคับ)** — ตั้งค่าโมเดลสำรองผ่าน `.env` ได้ รองรับหลายโมเดลเรียงลำดับ (ไล่ทีละตัวจนกว่าจะสำเร็จ) ถ้าโมเดลหลักชนโควตา **หรือตอบช้าเกินเพดานเวลาที่ตั้งไว้** ระบบจะลองโมเดลสำรองให้อัตโนมัติ ไม่ต้องรอหรือแก้โค้ด

## 🚀 เริ่มใช้งาน

**สิ่งที่ต้องมีก่อน:**
- Python 3.10+
- โฟลเดอร์ `models/` (โมเดล embedding + reranker)
- โฟลเดอร์เอกสารนโยบาย (`Policies/`, `Procedures/`, `Manuals/`, `Forms/`)
- Gemini API key ([ขอได้ฟรีที่ Google AI Studio](https://aistudio.google.com/apikey))

ไฟล์และโฟลเดอร์เหล่านี้ไม่ได้อยู่ใน git (ดูเหตุผลด้านล่าง) ต้องเตรียมเองในโฟลเดอร์โปรเจกต์

**⚠️ เช็คก่อนติดตั้ง — เตรียมพื้นที่ฮาร์ดดิสก์อย่างน้อย 15 GB**

ระบบนี้ใช้พื้นที่มากกว่าแอปทั่วไปพอสมควร เพราะเป็นโมเดล AI ที่รันบนเครื่อง ไม่ใช่แค่เรียก API:

| ส่วน | พื้นที่โดยประมาณ |
|---|---|
| Library ทั้งหมดใน `requirements.txt` (หลักๆ คือ PyTorch + LlamaIndex) | ~5-7 GB |
| โมเดล embedding (BGE-M3) + reranker (BGE-reranker-v2-m3) ในโฟลเดอร์ `models/` | ~4-5 GB |
| ฐานข้อมูลค้นหา `storage/` ที่ `build_index.py` สร้าง | หลักสิบ MB ต่อเอกสารนโยบายทั่วไป (ยิ่งเอกสารเยอะยิ่งโต) |

**เรื่อง GPU:** ไม่จำเป็นต้องมี — ระบบออกแบบมาให้รันบน CPU ได้ปกติ (ครั้งแรกจึงรอโหลดโมเดล ~4-5 นาทีตามที่ระบุด้านล่าง) ถ้ามีการ์ดจอ NVIDIA และอยากให้ขั้นตอน `build_index.py` และการโหลดโมเดลเร็วขึ้น ต้องติดตั้ง PyTorch รุ่นรองรับ CUDA เองแยกต่างหาก **ก่อน** รัน `pip install -r requirements.txt` เพราะรุ่นที่ได้จากไฟล์นี้เป็น CPU-only โดยดีฟอลต์ — เลือกคำสั่งติดตั้งที่ตรงกับการ์ดจอได้ที่ [pytorch.org/get-started](https://pytorch.org/get-started/locally/)

1. คัดลอก `.env.example` เป็น `.env` แล้วใส่ API key และชื่อองค์กรของคุณ:
   ```
   GOOGLE_API_KEY=your-gemini-api-key-here
   COMPANY_NAME=บริษัทของคุณ จำกัด
   ```
2. ติดตั้ง dependencies:
   ```
   pip install -r requirements.txt
   ```
3. สร้างฐานข้อมูลค้นหาจากเอกสาร (ไม่ต้องติดตั้งอะไรเพิ่ม — ใช้ library ชุดเดียวกับขั้นตอนที่ 2 ทั้งหมด รันครั้งแรกก่อนใช้งาน และรันซ้ำทุกครั้งที่มีเอกสารเพิ่ม/แก้ไข):
   ```
   python build_index.py
   ```
   ขั้นตอนนี้ใช้เวลาประมาณ 4-5 นาที ผลลัพธ์คือโฟลเดอร์ `storage/` ที่แอปจะโหลดตอนเริ่มทำงาน
4. รัน `run_app.bat`
5. รอครั้งแรกประมาณ 4 นาที (โหลดโมเดล) ครั้งต่อไปจะเร็วขึ้นมากเพราะโมเดลถูกโหลดค้างไว้เบื้องหลัง

ต้องการปิดระบบให้สนิท (บังคับให้โหลดโมเดลใหม่ในรอบถัดไป เช่น หลังอัปเดตเอกสาร) รัน `stop_worker.bat`

## 📝 โหมดร่างเอกสาร (ทดลอง)

โหมดถาม-ตอบปกติจะตอบเฉพาะสิ่งที่มีอยู่ในเอกสารจริงเท่านั้น (กันตอบมั่ว) แต่บางครั้งคุณต้องการ **ร่างนโยบายใหม่ที่ยังไม่มีอยู่** เช่น "นโยบายจัดซื้อ" หรือ "นโยบาย PDPA" — โหมดนี้ทำสิ่งนั้นให้ พร้อมถามข้อมูลที่จำเป็นก่อน และตรวจสอบตัวเองก่อนส่งถึงคุณ

**วิธีใช้:** เปิด toggle "📝 โหมดร่างเอกสาร (ทดลอง)" ในไซด์บาร์ แล้วทำ 2 ขั้นตอน:

1. กรอกหัวข้อนโยบาย (และรายละเอียดเพิ่มเติมถ้ามี) → กด **"❓ สร้างคำถามเพิ่มเติม"** — ระบบจะเทียบกับนโยบายที่มีอยู่แล้ว แล้วถามเฉพาะข้อมูลที่ยังขาด (เช่น หัวข้อ "นโยบาย PDPA" จะถามเรื่องข้อมูลส่วนบุคคลที่เก็บ, มี DPO ไหม ฯลฯ ที่ไม่มีอยู่ในนโยบาย IT/Risk Management เดิม) คำถามแบ่งเป็นหมวดหมู่และละเอียดขึ้นกว่าเดิม ถามทีละข้อ (ไม่ใช่ฟอร์มเดียวรวด) ย้อนกลับไปแก้คำตอบก่อนหน้าได้ และก่อนแต่ละข้อระบบจะเสนอคำตอบที่น่าจะเป็นจากเอกสารจริงมาให้ยืนยัน/แก้ก่อนเสมอ (Prefill) ตอบเท่าที่รู้ได้ ข้อไหนไม่แน่ใจข้ามได้เลย ไม่บังคับตอบครบ
2. กด **"✅ ยืนยันร่างนโยบาย"** — ระบบร่างเอกสารจากข้อมูลที่มี แล้ววิจารณ์ตัวเองทันที

**สิ่งที่ได้:**
1. ร่างนโยบายฉบับเต็ม (Markdown) อ้างอิงรูปแบบ/หลักการจากนโยบายที่มีอยู่แล้วในระบบ — จุดไหนที่คุณข้ามคำถามไม่ตอบ ระบบจะใส่เครื่องหมาย `[ต้องระบุ: ...]` ไว้แทนการเดาคำตอบขึ้นมาเอง
2. รายงานตรวจสอบทันที — ระบบวิจารณ์ร่างของตัวเองเทียบกับนโยบายเดิม แบ่งเป็น 4 ระดับ: **CRITICAL** (ขัดแย้งชัดเจน/เสี่ยงสูง), **WARNING** (ควรตรวจก่อนใช้จริง — รวมถึงจุดที่มี `[ต้องระบุ: ...]` ค้างอยู่), **NITPICK** (จุดเล็กน้อย), **VERDICT** (สรุป 1 บรรทัด)
3. ปุ่มดาวน์โหลดเป็นไฟล์ Word (.docx)

**ข้อควรรู้:**
- ⚠️ **ร่างนี้ไม่ใช่เอกสารสำเร็จรูป** ต้องมีมนุษย์ตรวจสอบและอนุมัติก่อนนำไปใช้จริงเสมอ — ต่อให้รายงานตรวจสอบไม่พบ CRITICAL ก็ตาม ระบบจะไม่บล็อกการดาวน์โหลดแม้เจอ CRITICAL เพราะร่างเป็นแค่จุดเริ่มต้นให้คุณไปแก้ต่อ ไม่ใช่คำตัดสินสุดท้าย
- ไฟล์ .docx ที่ได้เป็นโครงสร้างเปล่า (หัวข้อ/ย่อหน้า/bullet) **ไม่ตรงกับ template จริงขององค์กร** (ไม่มีตารางเซ็นสั่ง/ทวนสอบ, ประวัติแก้ไข, หัวกระดาษ) — คัดลอกเนื้อหาไปวางใน template จริงเองก่อนเสนออนุมัติ
- ใช้โมเดล Gemini แยกจากโหมดถาม-ตอบปกติ (ปรับได้ผ่าน `GEMINI_MODEL_DRAFT` ใน `.env` ค่าเริ่มต้น `gemini-3.5-flash`) เพราะงานแต่ง+วิจารณ์เอกสารต้องการ reasoning มากกว่างานค้นหาล้วน ต้นทุนต่อครั้งจึงสูงกว่าการถามคำถามปกติ ส่วนขั้นตอนสร้างคำถามเพิ่มเติมใช้โมเดลเดียวกับ Q&A ปกติ (`GEMINI_MODEL_CHAT`) เพราะเป็นงานเบากว่า
- หลังยืนยันร่างสำเร็จ ปิด toggle โหมดร่างเอกสารแล้วกลับไปที่แชทปกติ จะเห็นแบนเนอร์แจ้งว่าเซสชันนี้มีร่างที่คุยต่อได้ — ใช้ได้แค่ในเซสชันเดียวกัน (แท็บ/หน้าต่างเดิม) เท่านั้น ปิดหรือรีเฟรชหน้าเว็บแล้วร่างจะหายไปจากความจำแชท (ไม่ได้ลบไฟล์ .docx ที่ดาวน์โหลดไปแล้ว)

## 📋 โหมดรีวิวเอกสาร (ทดลอง)

แยกจากโหมดร่างเอกสารด้านบนโดยสิ้นเชิง — ใช้ตอนต้องการ **"ตรวจทาน" นโยบายที่มีอยู่แล้ว** (ไม่ใช่แต่งใหม่) เช่น ทบทวนนโยบายจัดซื้อประจำปี หรือเช็คว่านโยบายเก่ายังสอดคล้องกับเอกสารอื่นที่เกี่ยวข้องอยู่ไหม

**วิธีใช้:** เปิด toggle "📋 โหมดรีวิวเอกสาร" ในไซด์บาร์ แล้วทำตามขั้นตอน:

1. เลือกเอกสารเป้าหมาย — อัปโหลดไฟล์ใหม่ตรงได้เลย (ไม่ต้องรัน `build_index.py` ก่อน) หรือเลือกจากเอกสารที่มีอยู่แล้วในระบบ
2. ระบบวิเคราะห์โครงสร้างหัวข้อของเอกสารนั้นอัตโนมัติ (จาก heading จริงในเอกสาร) ผสมกับ checklist เฉพาะประเภทเอกสารสำหรับสิ่งที่เอกสารเดิมไม่มีเลย พร้อมแนะนำเอกสารอื่นที่เกี่ยวข้อง (cross-reference) ให้ยืนยัน/เพิ่มเอง
3. เดินตรวจทีละหัวข้อ ย้อนกลับไปแก้ได้ — ก่อนแต่ละหัวข้อระบบจะเสนอคำตอบที่น่าจะเป็นจากเอกสารจริงมาให้ยืนยัน/แก้ก่อนเสมอ (Prefill พร้อมวันที่มีผล/แก้ไขล่าสุดของเอกสารอ้างอิงกำกับไว้ ให้คุณตัดสินใจเองว่ายังใช้ได้อยู่ไหม)
4. เมื่อครบทุกหัวข้อ ระบบสรุป **รายงานการเปลี่ยนแปลง + เอกสารฉบับปรับปรุง** ให้คู่กัน

**ข้อควรรู้:**
- ⚠️ เอกสารเป้าหมายที่เขียนเป็นพรืดเดียวไม่มีโครงสร้างหัวข้อชัดเจน (เช่น PDF สแกนภาพ, ไม่มี heading) ระบบจะ **ปฏิเสธและแนะนำให้ใช้โหมดร่างเอกสารแทน** — ไม่ fallback เป็น checklist เดาเอาเงียบๆ
- ผลลัพธ์เป็นแค่จุดเริ่มต้นให้ทีมตรวจสอบต่อ เหมือนโหมดร่างเอกสาร — **ต้องผ่านการอนุมัติจากมนุษย์ก่อนใช้งานจริงเสมอ**
- ไม่มีการบันทึกความคืบหน้าข้ามเซสชัน — ปิด/รีเฟรชหน้าเว็บระหว่างรีวิว ต้องเริ่มใหม่
- ใช้โมเดล `GEMINI_MODEL_DRAFT` เดียวกับโหมดร่างเอกสาร (งานซับซ้อนกว่า Q&A ปกติ)

## 🔁 สลับโมเดลสำรองอัตโนมัติเมื่อชนโควตาหรือค้างนาน (ไม่บังคับ)

ถ้าใช้งานหนักจนโมเดลหลักชนโควตา (429 / RESOURCE_EXHAUSTED) บ่อยๆ **หรือโมเดลหลักตอบช้าจนเกินเพดานเวลาที่ตั้งไว้** ตั้งค่าโมเดลสำรองไว้ใน `.env` ได้ — รองรับหลายโมเดลเรียงลำดับ คั่นด้วยคอมมา ระบบจะไล่ลองทีละตัวจนกว่าจะสำเร็จ:

```
GEMINI_MODEL_CHAT_FALLBACK=gemma-4-26b-a4b-it,gemini-2.5-flash-lite,gemini-3-flash-preview,gemini-2.5-flash
GEMINI_MODEL_DRAFT_FALLBACK=gemma-4-31b-it,gemma-4-26b-a4b-it,gemini-3-flash-preview,gemini-2.5-flash
```

(ตั้งค่าโมเดลเดียวแบบเดิมก็ยังใช้ได้ปกติ เช่น `GEMINI_MODEL_CHAT_FALLBACK=gemma-4-26b-a4b-it` — ระบบมองเป็น chain ที่มีสมาชิกตัวเดียว)

⚠️ **ต้องใช้ชื่อโมเดลตามที่ Gemini API รองรับเป๊ะๆ** — Gemma 4 เข้าถึงผ่าน Gemini API ได้เฉพาะชื่อที่มี `-it` ต่อท้ายเท่านั้น (`gemma-4-26b-a4b-it`, `gemma-4-31b-it`) ชื่อแบบสั้น (`gemma-4-26b`) จะเจอ `404 NOT_FOUND` ทันที

ระบบจะลองโมเดลสำรองอัตโนมัติเมื่อโมเดลหลัก **retry ครบ 3 ครั้งแล้วยังชนโควตาอยู่ หรือค้างเกินเพดานเวลาที่ตั้งไว้** (ไม่ fallback ทันทีถ้า error ไม่ใช่เรื่องโควตา/timeout) ค่าเริ่มต้นเป็นค่าว่าง = ปิดฟีเจอร์นี้ พฤติกรรมเหมือนเดิมทุกประการ

**เพดานเวลาต่อคำขอ** ปรับได้ผ่าน `GEMINI_REQUEST_TIMEOUT_MS` ใน `.env` (ดีฟอลต์ 5 นาที) — ถ้าโมเดลหลักไม่ตอบภายในเวลานี้ ระบบจะตัดและลองโมเดลสำรองต่อ (หรือแจ้ง error ชัดเจนถ้าไม่มีโมเดลสำรองตั้งไว้) แทนที่จะค้างไม่มีที่สิ้นสุด

**ก่อนตั้งค่าใช้งานจริง — ทดสอบโมเดลสำรองแยกเดี่ยวก่อนเสมอ:**
```
venv\Scripts\python.exe test_fallback_model.py gemma-4-26b-a4b-it
```
สคริปต์นี้เรียกโมเดลตรงๆ ไม่ผ่าน worker/แอป ถ้าโมเดลที่เลือกใช้ไม่ได้จริง (เช่น ชื่อโมเดลไม่ตรง หรือไม่รองรับผ่าน `GoogleGenAI`) จะเห็น error ทันทีตรงนี้ ดีกว่าไปเจอตอนโควตาโมเดลหลักหมดจริงแล้ว fallback ก็ error ซ้อน error

**ข้อควรรู้:** คำตอบบางครั้งอาจมาจากคนละโมเดลกันในเซสชันเดียวกันโดยไม่แจ้งเตือน ควรทดสอบคุณภาพของโมเดลสำรองที่เลือกก่อนตั้งค่าไว้จริงจัง (ดู ADR-003)

## 🧹 Session cleanup (อัตโนมัติ)

Session แชท/ร่างเอกสารที่ไม่ได้ใช้งานเกิน `SESSION_IDLE_TIMEOUT_SECONDS` (ดีฟอลต์ 8 ชั่วโมง ปรับได้ผ่าน `.env`) จะถูกลบออกจากความจำของ worker อัตโนมัติทุก 10 นาที ป้องกันไม่ให้ worker กินแรมโตขึ้นเรื่อยๆ ถ้าปล่อยรันต่อเนื่องเป็นวันๆ ไม่ต้องทำอะไรเพิ่ม ระบบจัดการให้เอง (ดู ADR-005)

## 🏗️ โครงสร้างระบบ

แอปแบ่งเป็น 2 โปรเซสแยกกัน คุยกันผ่าน local HTTP:

- **`app.py`** — หน้าเว็บ Streamlit ที่ผู้ใช้เห็น เบามาก ไม่มีการประมวลผล AI ใดๆ อยู่ในตัวเอง
- **`rag_worker.py`** — โปรเซสเบื้องหลังที่ทำงานหนักทั้งหมด (ค้นเอกสาร + เรียก Gemini) แยกจาก Streamlit โดยสิ้นเชิง

**เหตุผลที่แยก:** ระหว่างพัฒนา พบว่าถ้าใส่โมเดล AI ไว้ในโปรเซสเดียวกับ Streamlit บน Windows แอปจะค้างหรือปิดตัวเองแบบสุ่มหลังใช้งานไปสักพัก การแยกโปรเซสตัดปัญหานี้ได้ และเป็นผลพลอยได้คือรีสตาร์ทหน้าเว็บได้เร็วขึ้นด้วย (ไม่ต้องโหลดโมเดลใหม่ทุกครั้ง)

ไฟล์อื่นๆ ในโปรเจกต์:
- `build_index.py` — สร้าง/rebuild ฐานข้อมูลค้นหา (`storage/`) จากเอกสารในโฟลเดอร์ `Policies/Procedures/Manuals/Forms` — ต้องรันใหม่ทุกครั้งที่มีเอกสารเพิ่ม
- `extract_forms.py`, `convert_forms_to_txt.py`, `dump_raw_forms.py` — เครื่องมือแปลงไฟล์แบบฟอร์มดิบให้เป็น Markdown ก่อนเข้าระบบ
- `generate_docx.py` — แปลง Markdown เป็นไฟล์ .docx ใช้โดยโหมดร่างเอกสาร (ดูด้านบน)
- `test_rag_pipeline.py` — ทดสอบว่าระบบทำงานถูกต้องแบบ end-to-end (ไม่ต้องเปิด Streamlit ก่อน) รันด้วย `python test_rag_pipeline.py`
- `test_fallback_model.py` — ทดสอบแยกเดี่ยวว่าโมเดลที่จะตั้งเป็น fallback เรียกผ่าน `GoogleGenAI` ได้จริงไหม ก่อนตั้งค่าใน `.env` จริง (ดู หัวข้อ "สลับโมเดลอัตโนมัติเมื่อชนโควตา" ด้านบน)

## 🩺 แก้ปัญหาเบื้องต้น

- **หน้าเว็บค้างที่ "กำลังเริ่ม RAG worker process..." นานเกินไป** — เช็คไฟล์ `rag_worker.log` ในโฟลเดอร์โปรเจกต์ จะบอกสาเหตุ (เช่น หา `.env`/โมเดลไม่เจอ)

- **อยากรู้ว่า worker ยังทำงานอยู่ไหม** — เปิด Task Manager หา process `python.exe` ที่ไม่ได้ผูกกับหน้าต่าง terminal ไหนเลย
